# The Shape of CoherenceMCP

CoherenceMCP exists for one person in one situation. Someone has a project, anything from a sentence like "build me a game that plays like this" or "make a website for my business that does that" to a half-built codebase with a long conversation behind it. They want a finished product that matches what they meant, and they don't want to stand over an agent supplying everything it didn't know. The agent's default behavior works against them. Every value it isn't given gets filled with the most probable answer from its training, which is the average version of the thing, polished and competent and belonging to no one. CoherenceMCP is the instrument that stops that from happening. It gives the agent a fixed procedure that derives every value of the project from a real source. It holds the result in a record the agent can't drift away from. It asks the person for exactly one judgment, made at the foundation. And it proves at the end that the built product contains nothing the record didn't settle.

It is not a task tracker, because a list of tasks says nothing about whether the tasks are the right ones. It is not a spec writer, because a long prose spec is decoded through the same averages that produce slop, and nobody can read it. It is not a taste engine, because the server checks structure and never rules on beauty; taste comes from the person and from work real people made. And it runs where the project lives, because its final check reads the project's own files.

The procedure starts from the cause of the problem. A model asked for a value produces something near the most probable value given its context. Neither describing a value in words nor reasoning harder about it adds information about this particular project. Roughly, what the finished product can know about the project is bounded by what the starting material and the gathered evidence contain, and the model's training fills in the rest with the average. Every part of CoherenceMCP is therefore a way of bringing information in, from the person, the world, existing work, and observation of what was built, and a way of refusing values that came from nowhere.

The same reasoning rules out the two designs Taskmaster tried before. A fixed sequence of content steps can't fit every project. A sequence the agent derives for itself is just another output, so it comes out as the average workflow. What gets fixed instead is a set of questions. They are always the same, always asked in the same order, and each one demands an answer in a particular form. Which questions get asked about what is determined by the project, through a walk that finds what is still open. The procedure is fixed, and the work it generates belongs to the project, the way a grammar's rules are fixed while the sentences they generate are not.

The unit of the record is a point. A point is something in the project that is not yet determined by what is already settled, raised as a question, and it holds whatever answers have been given to it. Every point has parents: the settled points it was raised from, which it serves. That makes the record a graph rooted at a single point every project has, the root. The root asks what the project is for, for whom, and what it refuses to be.

Points have kinds, and the kind says what the point is about. A situation is a moment in a person's time with the product. A family is a body of existing work chosen to carry many parts at once, such as a design system, an asset pack and its art style, an animation set, or an engine. A job is something that has to be made for a situation to happen. A tension is a place where two things the project wants pull in opposite directions. A question point is one of the person's own questions, raised automatically at the start so that it can't be lost.

Root, question, situation, family, and tension points form the approval level: the part of the graph the person judges. Job points sit below it. A job can change during the build without coming back to the person, as long as nothing above it moves.

Before a point is answered, it passes a gate with two conditions. It has to matter, meaning a different answer would change something for the person using the product. And it has to be open, meaning more than one answer is defensible given what is settled. A point that doesn't matter is dropped with its reason. A point that isn't open is a consequence, so it gets only the rule that produces it and the values that rule yields; text size following from reading distance is an example. Only real decisions receive the full questions, which keeps the record the size of the project's genuine choices instead of turning it into bookkeeping.

A decision receives seven questions, in this order, and the order is part of the design.

The first asks what the point serves. The answer explains how it serves its parents, and through them the root. That is the method's preservation condition made structural: a point preserves the purpose exactly when a path connects it to the purpose.

The second asks what happens to a person at this point. The answer must be a situation: who is there, what they can perceive, what they can do, and what follows. Deep in the construction, it becomes the job: what must be true for the situation above it to happen. Adjectives are not accepted, because they decode into the average. Jargon fails for the same reason. Measurements fail because at this stage they are guesses dressed as facts.

The third asks what the average version of this kind of project would do here, stated concretely before anything is chosen. This turns the model's training from a source of values into a detector of defaults. It also keeps the next answer honest, because the typical choice is already on the page beside whatever gets decided.

The fourth asks what this project does instead. It requires the decision, the concrete alternatives it excludes, and the reason. If the decision agrees with the average, the agent must say so, and the reason must then rest on evidence specific to this project, not on familiarity.

The fifth asks who has already done this well. The answer names the existing work that was actually examined, the piece chosen, its license, what is kept, and what is changed. What gets kept is whatever makes the work function: its tested proportions, timing, and handling of states. What gets changed is whatever makes it belong to this project: its content and the project's settled shared choices. Only when no existing work fits does the answer become custom construction, with the reason and the condition the custom work must meet. Families and jobs must answer this question; other kinds may.

The sixth asks what observation would show the decision to be wrong.

The seventh asks what the decision leaves open. The answer is a list of new points, each with an identifier, a kind, and a question. This is what makes the procedure recursive.

Every decision carries its sources and a confidence. The permitted sources are deliberately few. The person's words, quoted, must appear verbatim in the request, and the server checks this. Conversation passages, quoted, must appear verbatim in the context supplied at the start, and the server checks that too. Research needs a link and a quoted passage. Existing work needs an exact reference. Derivation needs the settled points it was derived from. Observation needs what was observed and what it showed. Phrases such as "best practice," "industry standard," and "users expect" are refused, because they are the average describing itself.

Every decision also writes into the manifest whatever concrete values the build will need from it. The manifest is a pinned list in the sense of a software lockfile. Every piece of reused work appears as a resolvable reference, meaning a link, a package and version, or a path. Every concrete value the product will use appears either as a token, as content, or as a rule. Values that can only be settled by looking at the built thing appear as deferred entries, each carrying the condition it must meet. Text the product will show belongs in the manifest too, because content left for the builder to write is the most common silent default there is.

Open points are found by walking, not by listing, because asking an agent to list a project's decisions retrieves the average list. One walk follows a person's time with the product, from the first moment they meet it to the moment the purpose is met. The other follows the construction, the way a builder would meet it. Wherever either walk reaches something the settled points don't determine, that is a new point. The server accepts a walk only if the experience walk names every settled situation and the construction walk names every settled family and job. The walk must pass through the whole graph, and the experience walk becomes the account the person reads.

Derivation repeats until no point is open and a walk finds no gaps. That is a fixed point: the state where applying the procedure again changes nothing. It is the honest meaning of complete. It also satisfies the method's distinction between necessary and sufficient conditions. A list of required features can all be present without the purpose occurring. An unbroken walk from the first moment to the purpose, through settled points, is an argument that the purpose does occur.

Several pieces of mathematics shape what the server does with this record, and none of them is decoration.

The first is the derivative, in both directions. The method's composition is a chain, and the chain rule says the result's sensitivity to the project is the product of each step's sensitivity. A step that would answer the same way for any project has zero derivative with respect to this one. That is the precise definition of a default, and one such step cuts everything downstream off from the project. The third question is what makes that derivative checkable in practice. In the other direction, a point's influence on the purpose flows down the graph. The server approximates it by the number of points built on the point, and multiplies it by the point's stated uncertainty to get a risk score. Decision theory calls that product the value of information, and the method calls it effort allocation. The server uses it to put the riskiest calls in front of the person.

The second is constraint satisfaction, which gives coherence its meaning: all the decisions can hold at once. Vague decisions can't contradict anything, which is why they look coherent. Precise ones can be checked against their siblings, so the server shows each point the decisions of its siblings and parents while it is being answered.

The third is optimization, which appears only at the bottom of the record, in the deferred entries. Their values are tuned during the build against conditions stated in a situation's terms.

The fourth is version tracking of the kind build systems use. Every point and every manifest entry has a version. Every answer records the versions of its parents. When something changes, exactly its descendants become stale. A stale point is either re-answered or confirmed to still hold. Nothing else moves.

When the walks come back clean, the record enters review, and the server renders the shape as a projection of the graph. It is not a document the agent writes. It opens with the request in the person's own words, then the root: who the project is for, what it does for them, and what it refuses to be. Next comes the experience walk, which reads as an account of what it will be like to be the person the project is for. After that come the answers to the person's own questions, the families with the actual works chosen, and the tensions and how each was resolved. Then come the five decisions with the highest risk score, each with the observation that would prove it wrong. Then come the approval-level points that cite none of the person's words, so the person can see exactly where the agent spoke for them. Last come the values that won't be settled until the build, each with its condition.

The person reads this and approves or denies. A denial names what is wrong, and the agent maps that onto points. Those points reopen with the denial attached, so the re-answer has to address it, and exactly their descendants become stale. A refusal costs what it should and no more. An approval fixes the approval level at its current versions, so no later stage can change the root, the questions, the situations, the families, or the tensions without coming back to the person.

After approval, the same agent that derived the shape compiles it into orders. That agent holds the fullest understanding, and the intent is for a stronger model to write the orders and a cheaper one to carry them out. An order says:
- which points it realizes
- which manifest entries it may use
- which orders must finish first
- which files it will touch
- what check will show its situations now happen

The server refuses a compilation unless every family and job is realized by some order, every manifest entry is used by some order, the order dependencies form no cycle, and every order that builds on another order's point lists that order as a prerequisite. The compiler may also name token files: the files where the manifest's values are written down, such as design tokens, data files, content files, and asset lists. These are the only places literal values may live.

The build runs one order at a time. For each order, the server splices together exactly what that order needs from the record: its points with their decisions and exclusions, the chain of decisions up to the root, the manifest entries it may use, the exclusions it must not violate, the design guidance for the aspects its points concern, the token files, and its check. The builder sees nothing else and needs nothing else, because nothing important lives in the conversation. That is how a long build avoids losing things: it never depends on what the agent remembers.

The build happens under a closed world. Code refers to the manifest's values by name, through the token files, and never states a literal of its own. When an order is reported complete, the server itself scans the files that order touched. It looks for literal colors, lengths, durations, font families, and media references that don't come from the manifest, and it refuses completion while any remain. That scan is the backward half of the trace, and it is the part that catches silent defaults without anyone having to judge taste. Deferred values used by the order must be reported along with the observation that settled them.

When the builder reaches something no order covers, it doesn't choose. It raises a gap, which becomes a new point. If the gap would change something at the approval level, the approval is suspended until the person sees the change. Otherwise the gap is answered with the same seven questions and attached to the order that raised it. When an observation shows a settled point was wrong, that point is revised, and the version tracking reopens exactly what was built on it, including any orders that realized it.

An order counts as done only while the points it realized are still at the versions they had when it was completed. So a change upstream automatically returns the affected orders to pending, and nobody has to remember to redo them.

When every order is done, the record enters verification, and finishing the list of orders is not enough. The server checks the forward trace: every family and job is realized by a done order. It runs the backward scan over every touched file. It confirms every deferred value is settled. The agent then repeats the experience walk on the built product rather than on the plan, using its tools, naming every situation and what was observed. It also obtains an independent review from an agent that did not build the product, comparing the product against the approved shape. A builder grading its own work is the weakest check there is.

Only when the traces are clean, the walk covers every situation, and the review is recorded does the record reach done. The claim that the coherent image has been built then means something specific and checkable.

The server is written to the agent's limits. A small model probably cannot hold a whole project and the whole procedure across a long run, but this design never asks it to. The server carries the procedure, the order of work, the state, the form checks, and the context. The model is handed one bounded step at a time with exactly what that step depends on.

That division of labor is also what makes a small local model plausible as the agent, and it is why the server keeps a step log. Every packet the server hands out and every call it accepts in return are written to steps.jsonl inside the project, so each session, whether a strong model or a local one drives it, is a record of single bounded steps paired with accepted answers, and the person's approval of the shape marks which sessions were coherent rather than merely well formed. How those records become training examples, which base model is adapted, and how the result is judged are decided in the local training work, by running this same procedure on that effort, not here.

None of this makes slop impossible. An agent can give answers in the right form with no substance behind them: stock imagery presented as a situation, a straw-man average set up to be departed from, work cited but never examined. The server can see form, not truth. That is why the person's single judgment at the foundation stays irreplaceable, and why the training effort is measured by whether different projects come out different. What CoherenceMCP guarantees is narrower and real. No value can enter the record without a stated source of a permitted kind. Nothing can be built that the record didn't settle without the server noticing. Nothing upstream can change without exactly its consequences reopening. And the person is asked for their judgment once, about the part of the project written in their own language.
